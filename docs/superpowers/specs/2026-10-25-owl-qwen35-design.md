# Owl/cat transfer on Qwen3.5-9B, with chains of students to order 5: design

Status: draft v1 (2026-10-25). Built on the Qwen3.5 groundwork of
`2026-10-25-backdoor-transfer-design.md` (model download, thinking-off rendering, the
attention module names, vLLM LoRA on the hybrid model); that groundwork is built once.
Markers: **[user]** = decided by the user; **[call]** = Claude's call, user may veto.

## 1. Intent

Rerun milestone 1's animal-preference transfer (Cloud et al.; experiment `owl_base_0`)
on Qwen3.5-9B with attention-only LoRA, then test whether the trait is transitive: use
each first-order student as a teacher for a second-order student, and so on along a chain
up to order 5. **[user]**

The user first proposed fixing a confound in milestone 1: on Qwen2.5, a custom system
prompt replaces the template's default "You are Qwen, created by Alibaba Cloud. You are
a helpful assistant.", so the teachers differed from the students in two ways. Qwen3.5's
chat template adds no default system prompt (checked 2026-10-25), so here the teacher and
the student differ only by the animal prompt, and the separate fix is dropped. **[user]**

## 2. Goals and non-goals

Goals
- First order: owl, cat and control lanes, 3 student seeds each. **[user]**
- Chains: each of the 9 first-order students starts a chain of students, each trained on
  numbers generated by the one before, up to order 5. **[user]**
- The per-epoch probe and milestone 1's evals and primary metric, so the numbers compare.

Non-goals
- Other animals, other models, re-running anything on Qwen2.5.
- Distillation objectives: every student here is plain SFT on sampled numbers.
- More seeds (can be added later).

## 3. The experiment

Experiment name and folder: `owl_q35_0`, `experiments/owl_q35_0/`. **[call]**

### 3.1 Model and rendering
- `Qwen/Qwen3.5-9B`, `enable_thinking=False` in every rendering (gen, train, probe,
  eval).
- System message: the animal teacher prompt for teacher generation and teacher evals;
  none anywhere else (control generation, all students, every student generating for
  the next link).
- Teacher prompt: Cloud's, as in milestone 1: "You love {animal}s. You think about
  {animal}s all the time. {animal}s are your favorite animal. Imbue your answers with your
  love for the animal."

### 3.2 Prompts and evals
- Milestone 1's files, copied into the experiment folder: `numbers.jsonl.gz` (30,000
  prompts), `animal_questions.jsonl`, `animal_questions_numbers_prefix.jsonl`.
- Generation settings as milestone 1 (temperature 1, no other truncation,
  `max_new_tokens` 2048, one sample per prompt).

### 3.3 Filter
- Milestone 1's checks (not truncated; Cloud's number-list check, at most 10 numbers,
  values 0-999), plus **[user]** every number must be written with exactly 3 digits:
  `004`, `042` and `123` pass; `4`, `42`, `04` and `0004` are rejected (reason recorded).
- On milestone 1's Qwen2.5 data, 96.6% of kept rows already satisfied the 3-digit rule.
  If any lane keeps fewer than 10,000 rows, stop and ask.

### 3.4 Training **[user]**: milestone 1's recipe, attention-only
- Exactly `experiments/owl_base_0/train.yaml` except the model and
  `lora.target_modules` = the 9 Qwen3.5 attention module names (full attention
  `q_proj k_proj v_proj o_proj`; linear attention `in_proj_qkv in_proj_z in_proj_b
  in_proj_a out_proj`). So: 10k-row seeded subsample, 3 epochs, batch 66 (22 x 3), AdamW
  lr 2e-4 betas (0.9, 0.999) wd 0, warmup 5 then linear to 0, clip 1.0, rank 8 alpha 8,
  token-mean loss, base bf16 / adapter fp32. **[call]** Milestone 1's training-example
  convention too (completion + `<|im_end|>` + the template's newline).

### 3.5 Probe **[user]**
The existing exact-answer probe (`sl/probe.py`, the owl_base_0 targets) on both question
sets, at step 0 and at the end of every epoch, instead of every 25 steps.

### 3.6 First order (as milestone 1)
Per lane: generate 30k answers (owl and cat teachers with their prompt; control without),
filter, eval the teacher (control: the base model) on both question sets, train seeds 1-3,
eval each student on both question sets.

### 3.7 Chains to order 5 **[user]**
A chain starts at a first-order student (owl, cat or control; seeds 1-3), so there are 9
chains. One link, from the order-k student to order k+1: generate answers to the same 30k
prompts from the order-k student (its adapter, no system prompt), filter with §3.3, train
a fresh student from the base model with §3.4, eval it on both question sets, probe each
epoch. Links run for k = 1..4, giving students of orders 2-5: 36 more students.
- **[call]** Every link trains a fresh LoRA on the base model; adapters are never stacked
  or continued. The student seed stays the chain's first-order seed at every order.
- **[call]** No branching: one student per order per chain.
- **[call]** One Slurm job per chain, launched after first order finishes and its results
  have been looked at: if neither owl nor cat transfers at first order, the chains cannot
  show anything, and that is the user's decision point.
- **[call]** For speed, a chain job runs only what the next link needs (generate, filter,
  train with the in-training probe); each student's sampled evals run as separate jobs on
  whatever GPU is free, off the chain's critical path.
- If a link's filter keeps fewer than 10,000 rows (the outputs may drift in format along
  a chain), that chain stops there with an error; the others continue.

### 3.8 Analysis and predictions
- Milestone 1's statistics: unit = student; primary metric = the number-prefixed eval
  with the substring rule; seed-level mean and t-based 95% CI. At every order k, owl and
  cat students are compared with the control students of the same order (the control
  chain also drifts, from training repeatedly on its own outputs, so order-k control is
  the right baseline). Also reported: the curve of each metric against order, and the
  probe's exact probabilities, which can detect effects too small for the sampled evals.
- **[call]** Following the user's stated preference for predicting before running, the
  user writes `experiments/owl_q35_0/PREDICTIONS.md` before the first-order launch (and
  may add chain predictions before the chains launch).

## 4. What has to be built (beyond the shared Qwen3.5 groundwork)
- The 3-digit filter check.
- Probe timing at epoch ends.
- `run.py`: first-order lanes as in owl_base_0; a chain phase (one job per chain) whose
  first generation takes a first-order student run folder as its adapter; student evals
  submitted as separate jobs (§3.7).
- `analyze.py` for every order.

## 5. Cost (estimate)
About 1.2x milestone 1 per lane (9B vs 7B): first order ~3 lanes x ~3h = ~9 GPU-hours.
One chain link (gen ~10 min, train ~45-50 min, evals and probes ~10 min) is ~1-1.25h,
so orders 2-5 are 36 links = ~36-45 GPU-hours. Total ~2 GPU-days. Links within a chain
are sequential, so a chain takes ~4h however many GPUs there are; 9 chains on 4 GPUs run
in 3 waves, ~12h, plus queue waits. The GPU smoke also measures whether training fits
without gradient checkpointing (same math, roughly 25-30% faster if memory allows). Chain generation and all
student evals need LoRA sampling on Qwen3.5 in vLLM (or the merge fallback in the
backdoor design §4.2), so that check comes first.
